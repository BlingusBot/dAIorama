# dAIorama — adversarial security/trust + network-surface audit (draft v1)

Lens: network surfaces, tokens, scopes, the view front, interop, threat posture.
Inputs: docs/00–11 at /home/agentuser/src/dAIorama (read-only) + docs/90-appendix/design-audit.md.
External facts checked against live sources (URLs at bottom): MCP 2025-06-18 transports/authorization/
security-best-practices, Claude Code MCP client config, wayvnc and noVNC auth capabilities.
Posture accepted as stated (config-level restrictions = harm reduction; container/OS isolation is the
real boundary). The test applied below is *implementability and coherence*, not "add more security".

Counts: **2 blockers, 8 majors, 3 minors (F1–F13)**.

---

## Findings

### F1 — The MCP wire presentation of BOTH credentials is unpinned; the flagship shape cannot be built without a decision — **blocker**
**Spec:** 07 §Scope model: *"network bridge: per-connection authentication — the connection presents scope name + scope secret, validated by the manager on the same presentation path as the instance token."*
Also 07 §surfaces: *"MCP bridge, network mode … instance token **and** per-connection scope auth"*; 04 §Global flags: *"`DAIORAMA_TOKEN` | Instance token for non-loopback access… never as a CLI argument"*.
**Problem:** The spec never says *how* a network MCP client presents anything. The pinned transport story is stdio (`DAIORAMA_SCOPE`/`DAIORAMA_SCOPE_TOKEN` "in the harness's own MCP client config", 07) and CLI env (`DAIORAMA_TOKEN` "alongside `--remote`"), but the flagship shape is an agent's container connecting to a published MCP port (09: *"published port (flagship — agent's container → dAIorama's container)"*). Over Streamable HTTP, MCP itself defines no static-secret presentation: stdio clients get env; HTTP clients get `Authorization` and the OAuth 2.1 discovery flow (MCP spec: *"Authorization is OPTIONAL… HTTP-based transport SHOULD conform to this specification"*). Static custom headers are the only practical channel (Claude Code documents `--header "X-API-Key: …"` and per-server `headers`), but their names, format, and per-request status are all unpinned, and there are **two unpinned hops**: harness→bridge and bridge→manager (the manager is the stated validator, so the scope secret crosses the bridge — pass-through or credential-holding proxy is undecided; pass-through is the MCP "token passthrough" anti-pattern in spirit).
**Why it matters:** Every flagship deployment config, the bridge's HTTP layer, and the manager validation path depend on this; also a spec-conforming client that receives 401 will attempt OAuth discovery, so failure behavior must be defined. This is exactly the class of gap (A3/A4) the spec claims closed.
**Disposition (decide before freeze, one paragraph in 07 + 05):** pin three request headers on the MCP endpoint — e.g. `Daiorama-Token`, `Daiorama-Scope`, `Daiorama-Scope-Token` — validated per request by the manager (bridge forwards them unmodified; bridge is a presentation relay, not a token authority); return MCP-level `scope_auth_required`/`token required` errors, never an OAuth `WWW-Authenticate` challenge; state explicitly that clients lacking custom-header support must use the container-local stdio shape (`daiorama mcp` with env, dialing the manager via `--manager`), and pin that recommended shape for the flagship (it needs no new MCP client capability).

### F2 — Operator identity over TCP is undefined; the instance token is shared by all agents — **blocker**
**Spec:** 07 §Scope model: *"Reserved scope `operator`: sessions created from the CLI carry it; CLI reads are operator-wide."*; 07 §surfaces: *"manager RPC … TCP bind requires instance token, always."*
**Problem:** In the shared shape every agent holds the instance token (F1 requires it at the bridge). Nothing says what the CLI presents over `--remote host:port`, nor whether the instance token alone confers `operator`. Both readings are broken: if token ⇒ operator, every agent can read all sessions/history and act operator-wide (the exact leak B8/A4 claimed to close); if not, the CLI has no defined way to authenticate as operator over the network (the `operator` scope has no stated secret, and "a scope without a secret cannot be used over the network").
**Why it matters:** The two-layer model (coarse network gate, finer scope identity) only coheres if identity ≠ transport token. As written, the CLI's own path is unspecified on the one shape the audit says scope auth is *for*.
**Disposition:** state in 07: the instance token is transport-only and confers no scope; over the unix socket the CLI's `operator` claim stays cooperative; over TCP the CLI must present the `operator` scope secret (define one in `scopes/operator.ron`; starter scope file from `config setup`), and `token show` prints a reminder of this. Error when a network client presents no scope: `scope_auth_required`.

### F3 — View-front credential mechanics are a name, not a flow — **major**
**Spec:** 07 §exposure rule: *"checks a token-derived credential (cookie or one-time code — a browser cannot send an Authorization header to a VNC endpoint, and wayvnc implements no such token), and proxies to a loopback wayvnc."*
**Problem:** Unpinned: (a) how a remote browser/consumer **obtains** the credential — `get_view` returns an "address", but the spec never says the credential rides in it, and `daiorama view` output is described only as "print the view address"; (b) **derivation** — "token-derived" must mean HMAC(instance token, view id/generation) so the instance token itself is never handed to MCP callers, but the spec doesn't say it; (c) **coverage** — page fetch is implied, static asset paths and the WebSocket upgrade are not named (a gate that only checks the page is cosmetic); (d) **multiplicity** — "cookie *or* one-time code" is two different mechanisms with opposite semantics: a one-time code is consumed by the first viewer, which contradicts the stated multi-consumer reality (dashboard viewer + agent's "realtime consumer" + a human); (e) no Origin/CSRF binding: WebSockets ignore CORS, so a cookie gate without an Origin allowlist on the upgrade is cross-site WebSocket hijackable; (f) the served noVNC page must ignore/whitelist client-supplied `host`/`port`/`path` params or the front becomes an open WS relay.
**Why it matters:** This is the A3 fix's load-bearing mechanism; the piece the spec calls "a real enforcer" is currently unimplementable without inventing the flow.
**Disposition:** replace with concrete text: the front mints a **per-view bearer credential** `credential = HMAC(instance token, view_id || generation)`, multi-use, valid for that view's generation only, revoked on `stop_view`/view death; `get_view`/`view` return the front URL with the credential as a query parameter (and session detail/status do not echo it); the front requires the credential on **every** request including static assets and the WS upgrade, rejects on mismatch, validates `Origin` on the upgrade, and serves noVNC with the WS target pinned server-side (params ignored). One-time codes are dropped from v1 (single-consumer semantics don't match the dashboard+agent reality).

### F4 — View address/port model breaks in the central shape; `get_view`'s "talk to it directly" is unreachable — **major**
**Spec:** 06 §Views: *"Port allocation: at view start … from `view.port_base` (6080, 04) upward, first free port"*; 05 §Views over MCP: *"the realtime consumer then talks to the returned address directly and never touches MCP again for perception"*; 07 §surfaces: view front default *"loopback"*.
**Problem:** (a) A view is two listeners (wayvnc + front) but the registry/port model allocates one port; which one `view.port_base` names, and where wayvnc's own loopback port comes from, is unstated. (b) In the flagship shape the front is loopback by default on the manager host, while the consumer is in another container: the returned address `127.0.0.1:6080` is unreachable, so the standing-stream perception pattern (and any dashboard viewer) only works when the operator separately exposes the front beyond loopback — and nothing specifies the credential delivery for the *agent* consumer in that case (the credential in F3 is browser-shaped).
**Why it matters:** Non-browser consumers (the stated flagship consumer) cannot "talk to the returned address directly" as written; the address is only meaningful in the embedded same-container shape.
**Disposition:** registry stores `{front_addr, front_port, vnc_port, generation}` with `front_port` allocated from `view.port_base` and wayvnc on an ephemeral loopback port; add one sentence: for `--remote`/network callers, `get_view` returns an address **relative to the caller's surface** — the bridge proxies `/view/<session>/…` (front stays loopback; the bridge is the only exposure) — or, if proxying is out of scope (VNC relay is a named non-goal in 01), state plainly that pushed streams require the front to be explicitly exposed and that `get_view` returns the credential-bearing URL for that case.

### F5 — The front/media gate is instance-wide, so scope isolation stops at the tool boundary — **major**
**Spec:** 05 §Views over MCP: *"The returned address is the manager-owned front (07): token-gated beyond loopback, same rule as everything else — not a separate per-session credential."*
**Problem:** Every network caller already holds the instance token (F1), so any authenticated caller can view **any** session's stream and fetch **any** `/media/<id>` whose URL/id it has seen, including across scopes meant to be "differently-trusted" (07/A4's stated motivation). The spec consciously chose instance-level gating but never states this consequence, and it silently negates per-scope isolation for perception surfaces that carry the most sensitive data (live desktop view, captured screenshots/clips).
**Why it matters:** The threat model on the shared shape says scopes separate differently-trusted callers; for the two surfaces that leak the most, they don't. Either accept it (then say so, and stop the scope language from implying otherwise) or fix the gate.
**Disposition:** add one sentence to 07: "View and media credentials are **instance-scoped, not scope-scoped**; a caller admitted to the instance can observe any session it knows the id of. Scopes constrain control and listing, not observation." If that is unacceptable, the minimal fix is to mint front/media credentials as HMAC over (scope, view/artifact id) and have the manager validate the scope claim first — the front already fronts everything, so the check point exists.

### F6 — Media endpoint: fetch auth, address family, and fetch-once lifetime don't survive their own edge cases — **major**
**Spec:** 05 §Capture/media: *"the artifact is deleted at first successful fetch or after TTL (default 60 s), whichever comes first"*; 07 §surfaces: *"media endpoint (`/media/<id>`) | on the manager surface | same rule as the surface it rides on."*
**Problem:** (a) **Fetch auth:** a `resource_link` URI is fetched out-of-band by the client's HTTP stack (MCP defines it as a resource the client "can be subscribed to or fetched"; nothing carries the MCP connection's headers to that fetch) — under the instance-token rule, a generic fetcher gets 401 (broken feature), and if the fix is a tokenized URL, that mechanism is unspecified. (b) **Address family:** "on the manager surface" means network-bridge callers get a URI on the manager's address, which is precisely what the agent's container cannot reach in the flagship shape (that is why the bridge exists) — identical navigability failure as F4, on a tool (`clip_video`) that is named in the pinned core surface. (c) **Races/resume:** two concurrent fetches race the delete; an interrupted or Range-resumed fetch after "first successful fetch" gets 404/410 by design; delete-on-first-fetch (or on response start?) is undefined; id entropy/length is unspecified for an opaque capability-ish id. (d) **TTL vs agentic latency:** 60 s is shorter than a typical background-fetch latency for a resource_link an agent may collect after the turn; also `audit.store_clips` persistence keeps the artifact but the endpoint id is gone — the fetchable copy and the persisted copy diverge.
**Why it matters:** `clip_video` is an advertised tool; as specified it fails for the flagship shape and has undefined behavior on normal (retry/resume) client behavior.
**Disposition:** pin: the manager mints the resource_link as a **single-use, TTL-bounded capability URL on the surface that served the call** (bridge rewrites on the way out; the bridge proxies `/media` to the manager — a `clip_video`-only proxy, not a general relay); delete happens only after the response body completes (`unlink` after final write; a deleted-but-open fd keeps serving concurrent readers); on a missed/expired fetch the error is `404` with the same `{code}` envelope (`media_expired`); concurrent-fetch rule stated (first completes wins, others finish; subsequent fetches fail); id = 128-bit opaque; raise TTL to a stated default that matches agentic latency (e.g. 15 min) or state that the TTL/“ephemeral” tradeoff is a decision the agent must handle by fetching immediately.

### F7 — Interop identity probe is spoofable, unpinned, and "explicit attachment" has no verb — **major**
**Spec:** 07 §Foreign sockets and interop: *"Any discovered socket is probed for protocol version + instance ID before any RPC. 'My socket' vs 'a foreign socket' is decided by that probe, never by path alone"*; *"Attachment is explicit, never a side effect of session creation."*
**Problem:** The probe is (per force) unauthenticated — any socket can answer it, so it decides nothing about trust; nothing states where an instance ID lives (08's path table has no instance-id file), who validates it, or what mismatches do (refuse? warn?). Nothing pins **ordering**: if the version handshake/connection presents `DAIORAMA_TOKEN` before the probe concludes, a hostile socket harvests the instance token (07 says the probe is "before any RPC", but token presentation is not a "session RPC" and its position in the sequence is unstated). And "attachment is explicit" has no implementation surface: 04's command tree has `--remote` but no attach/trust/pin command, so the guard is currently prose.
**Why it matters:** The B7 fix's stated purpose (stopping adoption of the wrong manager, and the boundary-inversion hazard) is only met if the identity check is meaningful and the credential sequence is pinned; otherwise the guard is theater with a token-leak footgun.
**Disposition:** state: probe is tokenless and precedes all credential presentation; instance ID is stored at `<data>/<instance>/instance-id` (0600), returned by the probe as `{protocol_version, min_supported, instance_id}`; first `--remote` attach to a new address records the id (TOFU pin) in the client config, later mismatches refuse with a distinct string unless `--re-pin`; document that the probe is unauthenticated so it is a routing aid, not a trust decision — the trust decision is the credential the caller then presents and the operator's explicit `--remote`.

### F8 — The bind-mount interop path makes "cooperative local" claims land on the shared shape — **major**
**Spec:** 07 §Scope model: *"local unix socket: scope claims are cooperative and documented as such"* and *"The shared/central shape, where differently-trusted callers come from different boxes, is where scope auth is real, and that is the network path."*
Also 07 §interop: *"The runtime-directory bind-mount trick is scoped to CLI/RPC discovery."*
**Problem:** The bind-mount trick gives a *different box* (a container) the tokenless, filesystem-gated unix socket — i.e., a cooperative-scope transport with full manager RPC (including claims like `operator`) on exactly the shape the spec designates as authenticated. The two sentences above are true of the TCP path and false of the bind-mount path, and the spec never reconciles them.
**Why it matters:** "Differently-trusted callers from different boxes" is the justification for the entire scope-auth addendum; the mount makes that justification shape-dependent, and an operator following the documented container interop pattern unknowingly gets the weaker model.
**Disposition:** add to 07: the bind-mount path grants the mounted container **instance trust** and cooperative scope claims — state it as a trust decision in the interop section (one sentence + a line in 10's ops notes), or require privileged scopes (`operator`, `dashboard`) to carry a secret even on the unix socket, or drop/scope the bind-mount pattern for shared instances.

### F9 — Dashboard exposure rule is self-referential; its credential flows are unnamed — **major**
**Spec:** 07 §surfaces: *"dashboard | loopback | same rule as everything else; its own manager connections carry per-connection tokens"*; 06 §History: *"The dashboard is a named scope with an explicit, documented broad-read grant."*
**Problem:** "Same rule as everything else" is "requires the instance token" — but the dashboard is multi-manager by design and has no single instance token; its own listener's credential, if it is ever exposed beyond loopback, is undefined, and what is behind it is a store of per-connection tokens for N managers (exposing the dashboard = lateral access to every manager it knows). Also unpinned: where the dashboard's `dashboard` scope secret lives (10 only stores per-manager *tokens* in the dashboard config), and which config key *is* the broad-read grant (06's `sessions.visibility = all` is phrased for MCP callers, not for a named scope).
**Why it matters:** D3/B8 are marked "adopted"; the flows are enumerated but the identity mechanics of the aggregating client are not, and the exposure row as written cannot be implemented.
**Disposition:** pick one: (a) v1 dashboard **refuses non-loopback binds** (remote humans reach it via SSH forward / overlay) — one sentence, strongest and consistent with "dashboard is local operator chrome"; or (b) the dashboard generates its own access token on first non-loopback bind (same lifecycle/UX as the instance token, its own path and `dashboard token show|rotate`), and `dashboard token set` additionally stores the `dashboard` scope secret per connection. Also name the broad-read key explicitly (e.g. a `read_scope` field in `scopes/dashboard.ron`).

### F10 — B9: `rate_limited` ships with no mechanism; shared shapes get no pacing — **major**
**Spec:** 07 §Rate limiting: *"Requirement: a per-session control-call rate cap exists for shared/central shapes; exceeded calls fail `rate_limited` (05). Mechanism is must-decide-before-ship for shared shapes."*
**Problem:** No mechanism, no default, no config key. Shipping the error code with no trigger makes it dead API surface; shipping no limiter on the shared shape means the "inhuman control rate is itself a detection signal" rationale — the project's reason to exist — has no enforcement anywhere, and the idempotency/retry rule ("retry once on `manager_unreachable` or timeout") does nothing for tight loops against a healthy manager.
**Why it matters:** It is the one open item with a stated must-decide-before-ship gate; the audit should not let it pass as prose.
**Disposition (minimal mechanism candidate, one paragraph in 07 + a key in 08):** per-session token bucket over **control-class** calls (input/mouse/keyboard/scroll; reads exempt) with scope-file config `limits.rate { per_sec = 20, burst = 40, mode = pace | reject }`; default `pace` for shared shapes = the manager delays execution of excess calls to the bucket rate (preserving the stealth goal and giving `idle-since`/input timestamps a human-plausible profile), `reject` = `rate_limited` with `hint: "retry_after_ms=<n>"`; the counter lives in the manager, keyed by session; document that pacing is also the natural place for future input-cadence shaping, so the mechanism is not thrown away.

### F11 — Persisted binary artifacts vs the text-history retention contract — **minor**
**Spec:** 05 §Capture/media: *"it is the same already-captured artifact that is additionally persisted to the data dir … retained under the history retention rules (08)"*; 04 §defaults: *"history | 8 segments × 4 MiB per session; retention 7 days after close."*
**Problem:** The history retention rules are sized for line-per-entry text (08 §History storage: "plain text, line-per-entry… buffered writer"). One PNG screenshot or a few seconds of clip video exceeds 4 MiB, so "retained under the history retention rules" either corrupts the rotation budget, silently drops just-persisted artifacts, or (if excluded) contradicts the sentence. Storage location, cap, and eviction for persisted media are unstated.
**Why it matters:** `audit.store_clips`/`store_screenshots` are the only reason artifacts persist; an operator enabling them for auditability gets undefined disk behavior and unknown retention.
**Disposition:** give persisted media its own explicit contract in 08: `<data>/media/` with its own cap (e.g. N MiB per session, oldest-first eviction) and the same 7-day post-close retention; state that the 8×4 MiB segment budget is text-only.

### F12 — Token hygiene details: print-once lands in logs; `token show --remote`; rotation window — **minor**
**Spec:** 07 §Token lifecycle: *"the path and value are printed once at that startup"*; 04 §Token: *"`daiorama token show` — print the local instance token (and its file path)."*; 07: *"the new token takes effect at next manager start."*
**Problem:** (a) The value is printed to stderr → journald/`docker logs`, which are persistent and commonly shipped off-host — the same exposure class the spec explicitly avoids for CLI args ("shell history, process listings"), so the hygiene rule contradicts itself. (b) `token show` is classified cold ("answers from files/void") and takes no stated position on `--remote`: as written, a remote call could fetch the remote token over the network or read the local file for a same-named instance — both need a pinned answer. (c) After `token rotate`, the file holds the new value while the running manager keeps accepting the old one: `token show` prints a not-yet-effective value; the output should say so (one clause), and 10's "rotate → restart → update env vars" should note the manager must not be restarted before clients are updated. (d) State explicitly that control-call arguments (which may contain user data, not secrets) are not recorded in history, since history carries "scope, origin, timestamps, cause" only.
**Why it matters:** All four are one-line contract additions where implementers would otherwise guess, and (a)/(b) are the only places the spec's own secret-hygiene stance is inconsistent.
**Disposition:** print only path + "run 'daiorama token show' for the value" at generation; pin `token show|rotate` as local-instance-only and explicitly refused with `--remote`; add the rotation-window clause.

### F13 — Posture vs gating language; circular media row; Origin validation absent — **minor**
**Spec:** 07 §exposure rule: *"The view port has a real enforcer now (A3)."* vs 07 §posture: *"None of these config-level restrictions are a security boundary…"*; 07 §surfaces: media row *"same rule as the surface it rides on"*.
**Problem:** (a) "Real enforcer" reads as a security claim inside a document whose posture says tokens are harm reduction — reword to "a real *gate for well-behaved callers*", or the two statements will be quoted against each other. (b) The media row is circular for callers reached via the bridge (which surface does it ride — manager or bridge? F6 needs one answer). (c) Neither the view front nor the dashboard states `Origin`/Host validation, which browsers require for cookie-gated HTTP+WS surfaces (and which MCP mandates for the bridge itself: *"Servers MUST validate the Origin header on all incoming connections to prevent DNS rebinding attacks"*).
**Why it matters:** Small, but each is a sentence a reviewer or implementer will trip over, and (c) is a one-line hardening requirement that belongs next to the gate it protects.
**Disposition:** reword the enforcer sentence; make the media row say "manager surface (bridge proxies per F6)"; add one line to 07: all manager-adjacent HTTP surfaces (bridge MCP endpoint, view front, dashboard) validate `Origin`/`Host` and bind loopback by default per the MCP transport warning.

## Verified OK (resolved claims and external facts that hold)

1. **A3** — the surface table now includes the bridge and dashboard; the gate is request-time (*"Bind-address checks are fragile the moment anything proxies or publishes a port"*); unix socket stays tokenless with the docker.sock rationale. Complete as an enumeration; the *mechanisms* are F3/F4.
2. **A5** — single generation rule is coherent and implementable (*"Generated on first non-loopback bind if none exists; written to `<data>/<instance>/token` (0600…)"* + the explicit "previous contradiction is resolved" note); rotation-drops-sessions is correctly tied to PDEATHSIG. Details in F12.
3. **A4** — a model is chosen, stated, and defensible as harm reduction; *"A claimed string is never authentication; a scope without a secret cannot be used over the network"* is the right sentence. Gaps are the *presentation* (F1) and the *operator/unix-mount* boundary cases (F2, F8).
4. **B7** — scoping the bind-mount to CLI/RPC discovery, the un-adoptable foreign compositor socket, and the boundary-inversion hazard as the guard's stated reason are all present and honest prose. Mechanism gaps in F7.
5. **B8** — history records carry scope + origin, reads obey session scoping, dashboard is a named scope with a non-default grant. Mechanism gaps in F9.
6. **D3** — connection CRUD, tokens in dashboard config (0600) rather than env vars (correct call for N connections), take-over states enumerated, rename label-only, view-down ≠ session-dead surfaced. Gaps in F3/F9.
7. **B9's decision hygiene** — an open item tracked with an explicit must-decide-before-ship gate is the right way to leave it; the requirement is on record rather than omitted.
8. **External: wayvnc/noVNC** — the front design is justified. wayvnc serves RFB-over-WebSocket only and never serves the noVNC HTML page (companion server required); noVNC's auth support (none, classical VNC, RealVNC RSA-AES, VeNCrypt Plain…) is compatible with a plain loopback wayvnc behind the front, while wayvnc's TLS security type is the noVNC-hostile one the prior audit flagged. wayvnc also supports multiple simultaneous clients (`client-list`, `connection_count`) — so the multi-viewer cases in F3 are a front-design question, not a wayvnc limit.
9. **External: MCP** — `resource_link` is a real 2025-06-18 content type (no video type exists, so 05's choice is the spec's own shape); stdio credentials-from-environment is the spec's stated mechanism; HTTP-transport auth is header-based and optional, so a static-header scheme is implementable for harnesses that support it (Claude Code: `--header`, per-server `headers`). This is what makes F1 a *decision* gap rather than an impossibility.
10. **Posture statement itself** — duplicated in 01 (principle 5) and 07 and internally consistent with "rootless, harm reduction, real boundary is isolation"; no audit finding invokes a security boundary the posture disclaims.

## Needs runtime test (cannot be settled on paper)

- **Cross-origin view credential delivery:** front sets cookie → dashboard-embedded viewer opens the WS from a *different site*: SameSite/Secure behavior on plain HTTP (candidate: only a code-in-URL flow works cross-site without TLS — F3's disposition assumes this; verify in two browser origins, including same-host-different-port).
- **Two simultaneous viewers** (human dashboard + a programmatic consumer) through one front to one wayvnc, including view restart mid-stream (credential must die and be re-minted with the new generation).
- **`/media/<id>` edge cases:** concurrent double fetch; interrupted download + retry; Range/resume after first fetch; slow client crossing the TTL; a real agent harness's fetch latency for a `resource_link` (is 60 s ever enough?).
- **Front as open proxy:** attempt to load the served noVNC page with client-supplied `host`/`port`/`path` pointed at an attacker WS endpoint (confirms F3(f) is actually closed by the implementation).
- **Harness matrix for F1:** Streamable-HTTP MCP clients beyond Claude Code (Cursor, VS Code, Codex, others) — can each attach two-three static headers per server, and what do they do on 401 without OAuth metadata?
- **WS through the front on a resized headless output** — the prior audit's wayvnc issue #326 (resize protocol error) now traverses an extra WS hop; exercise before claiming `--view` works headless.
