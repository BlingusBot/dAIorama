# dAIorama — Architecture & Design

## What this document is

This is the design reference for dAIorama. It exists so that anyone or anything building this, including an agent with no memory of how these decisions got made, can implement it correctly without having to guess, and without re-litigating decisions that were already made deliberately.

This document explains **what** dAIorama is supposed to do and **why** it's built the way it is. It deliberately avoids prescribing exact code structure, file layout, or algorithms — those are implementation choices for whoever builds this, and Rust gives plenty of good ways to express the ideas here. What it does *not* leave open to interpretation is behavior: command names, flags, defaults, and the contracts between components. Where a decision was made for a specific reason, the reason is included, because the reason is often what should guide a judgment call the doc doesn't explicitly cover.

If something in this document seems arbitrary, it probably isn't — read the rationale before changing it.

---

## 1. What dAIorama is

dAIorama gives an AI agent its own real desktop environment: a real compositor, a real browser, real windows, driven by real synthetic input at the operating-system level, the same way a human sitting at a remote desktop session would drive it. It is not a headless browser automation framework. It does not use a browser automation protocol (no CDP, no WebDriver) at all.

This matters for a concrete reason: automation protocols leave fingerprints. `navigator.webdriver`, headless flags, CDP artifacts — a sufficiently motivated website can detect all of it. A real browser, running in a real desktop session, driven by synthetic mouse and keyboard events at the compositor level, has none of that. It looks like a person using a computer, because structurally, that's what's happening.

dAIorama grew out of wanting to replace a fragile Camoufox-based (anti-detect headless browser) setup, but it is not scoped to that one project. It's a general-purpose tool: it should work equally well bundled into a single agent's own container, run as a shared "central" instance many agents point at, or installed bare on a normal Linux machine and pointed at a desktop that already exists.

The name reflects the core idea deliberately: the bot gets its own small, self-contained scene — its own diorama — to live in. dAIorama does not care about controlling *your* desktop. That it's technically capable of it in some configurations is a side effect of the architecture being simple and flexible, not a design goal.

## 2. Design principles

These aren't a checklist to satisfy once. They're the reasoning that should be applied to any decision this document doesn't explicitly cover.

**Rootless is a first-class citizen, not an afterthought.** Every technical choice in this document — the compositor, how GPU access works, how sockets are found — was filtered through "does this still work without root, specifically inside a rootless Podman container with `--cap-drop=ALL`." Needing root is treated as a sign the solution isn't clean yet, not as an acceptable fallback. If a future decision seems to require root, that's a signal to look for a different approach before accepting it.

**Lean by default, opt-in for everything else.** Nothing listens on a network port, nothing daemonizes, nothing spins up a desktop, unless something explicitly asked for it. A misconfigured or freshly-installed dAIorama should be inert, not accidentally exposed or accidentally running things nobody asked for.

**No implicit magic that a careless or buggy agent could turn into a runaway.** There is no default session. There is no "just create one for me" behavior anywhere in the MCP surface. Every action that touches a desktop requires an explicit session ID, and an agent that doesn't have one gets told to go create one — it never gets one handed to it automatically. This is deliberate: an agent stuck in a bad loop should fail loudly and cheaply, not quietly spawn a hundred desktops.

**Prefer composing with mature, purpose-built tools over reinventing hard infrastructure.** Wherever a problem already has a mature, audited solution — CDI for GPU device access, noVNC for browser-based VNC viewing, Tailscale or a reverse proxy for transport security — dAIorama should use it rather than build its own version. This project's job is the bridge between an agent and a desktop, not reinventing device permission handling or cryptography.

**Config-level restrictions are harm reduction, not security.** Anything dAIorama's own config can restrict, a caller with general code execution in the same environment can route around, because the compositor's input and screen-capture protocols grant capability to any client holding a socket connection — they don't check whether the request came through dAIorama's own CLI. Config limits (session quotas, tool allowlists) are worth having because they cheaply catch bugs and steer well-behaved agents with clear errors. They must never be treated as the thing standing between an agent and doing damage — that job belongs entirely to the container/OS isolation boundary (rootless Podman, dropped capabilities, only specific things crossing in or out).

**Build the general mechanism once; let configuration decide the shape.** Repeatedly in this design, something that looks like a fork in the road (one session or many, a single embedded instance or a shared central one, dashboard on or off) turned out to be the same underlying mechanism with a different config value, not two different things to build. Whenever a new feature seems to need "a simple version" and "a flexible version," look for whether it's actually the same mechanism first.

**Naming: technical inside, thematic outside.** Internal code names, RPC field names, and anything an agent has to reliably parse (MCP tool schema names, CLI flag names) stay plain and literal — clarity has a real, measurable cost to get wrong there. User-facing nouns get to use the diorama theme: a running desktop session is a **daiorama**, the manager process hosting one or more of them is an **exhibition**, and a dashboard aggregating across many exhibitions is a **museum**. `daemon` stays `daemon` — it's already the standard term, no need to reinvent it.

## 3. The compositor and the desktop

### 3.1 Hyprland, and why

Hyprland was chosen after directly comparing it against niri, which was seriously considered for its cleaner IPC and Rust/Smithay foundation. The comparison came out mixed, and it's worth recording honestly rather than pretending it was one-sided:

- niri has real, non-aesthetic advantages: Rust's memory safety removes whole classes of crashes in code that sits between the GPU and every client, which matters for something meant to run unattended, and niri's recent history has been steadier (no equivalent of Hyprland's disruptive config-format break).
- But for what dAIorama specifically needs *today*, Hyprland is ahead on the two axes that matter most. Its headless/no-display operation is a documented, stable, wiki-covered feature used in the wild for real remote/virtual-display deployments. niri's own documentation describes its headless backend as "used for automated testing," and there is an open, unresolved design discussion in niri's own repository about what a public headless/virtual-output API should even look like. Hyprland's virtual-input protocol support (mouse and keyboard injection) is confirmed complete; niri's has known gaps serious enough that a companion patch project exists specifically to work around them.
- There is already real prior art for exactly this use case built on Hyprland (an existing MCP bridge project using Hyprland's IPC plus its virtual-input protocols), which niri doesn't yet have an equivalent of.

Given all that, Hyprland is the compositor. This isn't a permanent, unquestionable choice — if Hyprland's headless path turns out to be unworkable in practice, niri (or a nested-compositor workaround, see below) is the documented fallback — but it's the right starting point.

### 3.2 Why a desktop, and why Wayland specifically, and why not root

The earlier alternative considered was a headless X11 stack (Xvfb + a minimal window manager). Wayland was chosen instead for a concrete, practical reason, not just preference: a small Wayland compositor is genuinely lighter (fewer dependencies, less surface area) than the equivalent X11 stack, and Wayland's virtual-input model turns out to be a better fit for staying rootless than X11 ever was.

This is the important part, and it's the reason Wayland won outright rather than just being "also viable": on X11, injecting synthetic mouse and keyboard input into a session from outside requires either the XTest extension (fine, works, but is a legacy free-for-all with weak access control) or, on Wayland generally, tools like `ydotool` which need access to `/dev/uinput`, a raw kernel input device that typically requires root or a specific elevated capability grant. That would have meant punching a hole in the exact rootless hardening this whole project is built around.

wlroots-family compositors — which Hyprland's protocol surface still matches even though it no longer depends on wlroots internally — solve this differently and better: `wlr-virtual-pointer-unstable-v1` and `virtual-keyboard-unstable-v1` are real Wayland protocol extensions. Any client holding a plain socket connection to the compositor can move the pointer and type through them. No `/dev/uinput`, no elevated capability, no root, ever. The access control lives entirely in the compositor's own policy, not the kernel — and since dAIorama is building and owning the entire session rather than injecting into someone else's, that policy can simply be "any client on this socket has full access," because there's no untrusted third party sharing that socket to protect against.

### 3.3 Backend modes

Hyprland can produce its output in three distinct ways. These are properties of the compositor, not of whether it's running in a container — the same three modes are available on bare metal:

- **`headless`** (default). No physical display attached at all. This is the mode used for containers and for any deployment with nothing else running. **Implementation note, not a decision to relitigate**: Hyprland has two different things that could be called "headless" — its own dedicated virtual-output feature (`hyprctl output create headless`), which has documented bug reports (black-screen rendering, GPU usage spikes) because it's really meant for adding an extra virtual monitor alongside a real one, and the plain DRM/TTY backend pointed at a GPU with no display connector at all (`AQ_NO_KMS_REQUIREMENT=1`), which is a much more heavily-exercised code path since it's the same one real render-only hardware (cloud GPUs, etc.) already relies on. Try the dedicated headless feature first, since that's the explicit decision, but if it proves flaky in practice, the render-only DRM path is the documented, more mature fallback under the same `headless` name — this is an implementation detail to resolve during building, not a reason to change the CLI surface.
- **`nested`**. Runs as an ordinary client window inside an already-running outer Wayland compositor, detected automatically via an existing `WAYLAND_DISPLAY`. This is what lets a human who's already daily-driving Hyprland (or any Wayland compositor) watch the bot's desktop live as a normal window on their own screen, with no VNC involved at all.
- **`host`**. The real DRM/TTY backend, against either a real display-capable GPU or a render-only one, with no nesting and no virtual-output trick. Named "host" rather than the more technical "DRM" or "TTY" deliberately — most people configuring an agent understand what MCP means, but far fewer know what DRM is, and "host" carries the same connotation Docker's `--network=host` already trained people on: skip the usual indirection, use the real thing directly. **`host` implies exclusive, DRM-master-style access to the real output, so it's one session at a time per manager** — two concurrent sessions both requesting `host` would conflict over the same physical connector. `headless` and `nested` have no such limit.

Selected via `--backend=headless|nested|host` on session creation; `headless` is the default. Screen resolution and DPI are also session-creation parameters, not left to whatever the backend defaults to — given the project's anti-detection goal (3.4), screen geometry is its own fingerprint, and a headless-typical default resolution is a known heuristic some sites check for. Dynamically changing resolution or adding/removing virtual outputs mid-session is deliberately not in scope for now (see section 10).

### 3.4 GPU access

GPU access is a hard requirement, not optional — Hyprland has a hard dependency on OpenGL with no software-only fallback path. It must also work without root, specifically inside rootless Podman, because that's the whole point of this project.

The key distinction that makes this possible: a GPU exposes two different kinds of device nodes. `/dev/dri/card0` (or similar) is the display/KMS node — it controls what's actually shown on a monitor, and using it for real requires DRM master privilege, historically tied to root or a logind session. `/dev/dri/renderD1xx` is the render node — it exists specifically to allow unprivileged compute and off-screen rendering, with access governed by ordinary Unix group permissions. dAIorama never needs the display node, since there's no physical monitor to control. Render node access is all that's required, and it needs no root at all.

**Everything below this point about device passthrough, group membership, and SELinux is specifically a containerized-deployment problem.** A bare-metal dAIorama process talking to the GPU on the machine it's actually running on has completely ordinary access to it, no different from any other desktop application — none of this applies outside a container. See section 9 for how this fits into the shipped image.

**AMD and Intel** (open Mesa driver stack): current documentation still describes the standard rootless recipe as passing the render node through with `--device /dev/dri/renderD128` and `--group-add keep-groups` (needs Podman's default `crun` runtime and host-user membership in the `render` group), plus `sudo setsebool -P container_use_devices=true` on SELinux-enforcing hosts if `getenforce` reports `Enforcing`. Treat that as a documented starting point to test against, not a settled recipe to build blindly on top of — the real picture right now is genuinely mixed, and worth being honest about rather than papering over:
- `--group-add keep-groups` has real, currently open Podman issues (as recent as this January) where a device's group shows up as `nobody`/unmapped inside the container even with the flag set. Several of those threads report the device still works despite the cosmetic ownership problem, but this is clearly an area with active rough edges in current Podman, not something to assume is smooth.
- The render node's own default permission mode is itself part of the uncertainty. Upstream systemd's own default udev rule sets `renderD*` to mode `0666` — world read/write, meaning group membership wouldn't matter at all if that default is actually in effect. But multiple current real-world reports, including inside the Podman issue threads above, show `crw-rw----` (`0660`, group-gated) instead. Which one is actually true on a given machine depends on the distro's own udev rule overrides, and this is plausibly the exact reason real experience diverges from generic guides. Running `ls -l /dev/dri/renderD128` on the actual target machine is the right first step, before assuming any particular flag combination is even necessary.

Don't lock in a specific recipe here from this document alone. Confirm what's actually needed against the real target environment during development — see section 11.

**NVIDIA**: this is not a permissions problem and treating it like one will lead nowhere. NVIDIA's driver is a large, closed, frequently-updated userspace blob that must version-match the host's kernel module exactly. A container's isolated filesystem view can't just have a generic copy of "the NVIDIA driver" baked in ahead of time — it needs to see the host's *actual, currently-installed* driver files, every time, which is a filesystem-visibility problem, not a security one. The fix is CDI (Container Device Interface): as of NVIDIA Container Toolkit v1.18, a systemd service on the host automatically generates and refreshes a CDI spec on install, driver upgrade, and reboot. Once that's installed (a standard one-time host step required by essentially every GPU container workload on NVIDIA, not something specific to dAIorama), the actual invocation becomes as simple as `--device nvidia.com/gpu=all`.

**What this means for the design**: never hardcode a device path anywhere in dAIorama's own code or the shipped image. Expose GPU device selection as a single config value that's either a render node path or a CDI device identifier, and provide a small bundled detection step (part of first-run setup, or its own command) that figures out which one applies and either configures it or tells the user the one thing they need to do.

Solving this correctly has a second, unrelated payoff worth knowing about: a container with no real GPU access renders WebGL content in software (`llvmpipe` or similar), and that software-renderer string is itself a real, checked-for automation signal on some sites, since real end-user machines essentially never show up with it. Getting real render-node access fixes both problems with the same fix.

**That second payoff is also where a silent failure here becomes a correctness bug, not just a performance one.** If GPU passthrough doesn't work on a given host and Hyprland quietly falls back to software rendering instead of refusing to start, dAIorama produces a session that looks completely functional and is secretly carrying the exact automation fingerprint this entire project exists to avoid — a misconfigured host would fail silently in the one way that matters most. This directly contradicts the "fail loudly and cheaply" principle in section 2 if left unhandled. Session startup must detect the actual active renderer (compositor-side, or a cheap WebGL-parameter check against a real browser once one's running) and either refuse to create the session or surface an unmissable warning — never let this degrade quietly into a session that looks fine and isn't.

## 4. Component architecture

There are four pieces. Understanding how they relate to each other matters more than any individual piece's implementation.

### 4.1 The manager (an "exhibition")

This is the one persistent process at the center of everything. It is lazily started — the first command that needs one and can't find one reachable starts it — and it works like a tmux server: once running, it stays running, and every later command is a thin RPC call against it over a local socket, not a fresh process.

**Starting it has an obvious race that needs a real fix, not just careful wording.** Two concurrent commands, neither finding a reachable manager, could both try to start one against the same runtime path at once. This needs an atomic lock acquired before anything attempts to bind or start a manager — a lockfile taken with `O_EXCL` or an flock, separate from the socket itself. Whichever process wins the lock starts the manager and creates the socket; the loser waits briefly and connects to the socket instead of starting a second one. Guarantee exactly one manager per runtime directory, don't leave this to timing.

The manager owns Hyprland and wayvnc as its direct children. Each child has `PR_SET_PDEATHSIG` set immediately after fork, before exec — this is the mechanism, not an implementation detail to skip, because it's what makes "if the manager dies, its sessions die with it" a real guarantee enforced by the kernel, rather than something that only works on a clean shutdown. A hard crash or `kill -9` of the manager still takes its children down. Because of this, **the session registry always starts empty after the manager itself restarts** — a prior manager's sessions are already gone by the time a new one could exist, so there's nothing to reconcile against. This is a direct consequence of the PDEATHSIG guarantee, not a separate decision, but it should be stated rather than left inferable.

A process being alive isn't the same as it being ready to use. The manager should periodically check that Hyprland's IPC socket actually responds to a trivial query, not just that the process still exists — a GPU driver hang or a deadlocked compositor thread can leave a process alive but completely unresponsive. A failed health check gets the same treatment as a crash: mark the session dead, don't auto-restart (see section 9's crash-handling policy, which this extends rather than duplicates).

The manager is also the single source of truth for two things regardless of who's watching: the current session registry (what sessions exist, their IDs, their status), and an append-only history log of every session and control call, tagged by its origin (shell or MCP). It writes that history continuously, whether or not a dashboard is running to read it — losing history because nobody happened to be watching would defeat the point of keeping it. **This log lives in a persistent data directory, not `$XDG_RUNTIME_DIR`** — the runtime directory is tmpfs and clears on logout or container restart, which would silently throw away history that's supposed to be exactly the kind of thing that outlives a session. And it's worth one honest caveat: this is an operational aid, not a tamper-evident audit trail — the same code-executing-agent caveat in section 4.3 applies here too, a caller that can route around config-level restrictions can presumably also alter its own history file. Don't treat it as forensic-grade.

SSD wear is a real constraint here, and it's worth being explicit about how the logging avoids it rather than just picking a small-looking format and hoping:
- **Write pattern is what actually causes wear, not format.** Don't fsync after every individual call — a buffered writer that flushes on a short interval or a small batch of entries, rather than forcing a physical write per call, is what keeps this cheap. Losing a few seconds of buffered-but-unflushed entries in a hard crash is an acceptable tradeoff here, since this history is an audit trail, not the source of truth for session state — that already lives in the registry itself.
- **The default has to be bounded, not just small so far.** History is scoped per session, size-capped with simple rotation (a handful of rotated segments, oldest dropped once the cap is hit), plus a configurable retention window after a session closes — delete immediately, or keep for a short grace period — rather than accumulating for the manager's entire lifetime. Plain, flat, line-per-entry text is the right format, not a database and not journald-style structured binary logging. Format was never really the risk here; unbounded retention and per-call fsyncs were.

**Foreground vs. background is not a decision the manager forces onto every invocation.** There are two explicit ways to run it: `daiorama serve`, which stays attached to the foreground (a container's main process, or an interactive terminal you're deliberately watching) so that its death or a signal to it cascades to everything it owns; and `daiorama daemon start` (with matching `status`/`end --force`), which explicitly detaches and persists in the background for bare-host use where the point is to survive closing your shell, or for wrapping in a systemd unit by someone who'd rather manage the process lifecycle themselves. When neither has been explicitly invoked and something just calls `daiorama new` directly, the manager should be started using whichever of the two behaviors fits the context it's actually running in (attached, if this looks like a container's main process or a fresh interactive shell with nothing else already running; backgrounded otherwise) — the point is that nobody has to think about this choice on the common path, while the explicit commands remain there, unambiguous, for whoever wants to force one or the other (a systemd unit should always call `daiorama serve` explicitly in its `ExecStart`, never rely on the automatic guess).

### 4.2 The MCP bridge

This is what a harness actually connects to. It speaks MCP on one side and talks to a manager's socket (local or remote) on the other. It is deliberately stateless with respect to session lifetime: if the bridge process dies and reconnects — a harness restart, a flaky connection — the session and its Hyprland/wayvnc processes are completely unaffected, because they belong to the manager, not to the bridge. This also means the bridge can be run either the classic MCP way (spawned per-connection over stdio by a harness, ephemeral, dying with that connection) or as a long-lived network service, whichever a given deployment needs — the bridge doesn't own anything that would make one of those modes wrong. In network-service mode, where one running bridge is the more likely reason to run it that way rather than per-connection, it reads the scope token from each incoming connection separately rather than being pinned to a single scope itself — scope is an application-layer identity carried on every call, not a property of the bridge process (see section 6).

**The same "a flaky connection shouldn't cost you a desktop" principle that protects the MCP-client-to-bridge relationship needs to extend one hop further, to the bridge-to-manager and dashboard-to-manager relationship.** If the manager becomes unreachable, mid-call or between calls, a transient network blip or the manager restarting, the bridge and dashboard should reconnect with backoff and surface a clear "manager unreachable" state, not a raw connection error — and once reconnected, confirm nothing about session state was lost (which, per 4.1, it structurally can't be unless the manager itself actually died).

**Important clarification, because it was genuinely ambiguous during design and needs to be settled here explicitly: there is no separate "daemon" hiding behind the manager and the CLI.** The manager *is* the only daemon that exists for a given instance. Its RPC surface simply covers more than session lifecycle — sessions, control actions, and config are all just different calls against the same running process. `--remote` always means exactly one thing: which running instance of this one daemon is this command talking to. A remote config change and a remote session creation are the same kind of call to the same kind of thing, just different verbs.

**The shared/central deployment shape (section 9) means the manager can get upgraded independently of, and at a different time than, the CLI and bridge binaries talking to it.** That needs a stated compatibility policy, not silence: the RPC surface should be additive-only (new fields and calls can appear; existing ones don't change shape or meaning), and the manager should reject a client that declares an incompatible version with a clear error rather than behaving unpredictably against a wire contract it doesn't actually match. A simple version field on the RPC handshake is enough for this — it doesn't need its own negotiation protocol, just a rule that's actually enforced. The manager's RPC surface should also expose a lightweight liveness/readiness call, distinct from a full session list, since the shared-instance shape means other things may reasonably depend on checking it's up.

### 4.3 Session and control scoping, security posture

Every session and control call requires an explicit, valid session ID. There is no implicit or default session anywhere in the MCP surface — an invalid or missing ID gets a clear error telling the caller to create a session first, never a silently auto-created one. This is deliberate, to stop a buggy or looping agent from spawning unbounded sessions by accident.

Each connecting caller carries a scope, set once as a token in that caller's own MCP client config. Session visibility and ownership default to own-sessions-only per scope; broader visibility across sessions is available only through deliberate configuration, never by default. Quotas (most importantly `max_sessions`) are configured per scope rather than globally, specifically so that someone running several differently-trusted agents on one bare-metal box can give each one its own limit instead of one blanket setting affecting all of them. **There should also be one global ceiling on total concurrent sessions per manager, enforced independently of the per-scope quotas** — on the shared/central deployment shape, several individually-reasonable per-scope limits can still sum to more GPU-backed desktop sessions than the host can actually run, and per-scope quotas alone don't catch that.

Quotas as written only limit how many sessions exist, not how fast a single valid session gets driven. That's worth its own stated concern, not generic abuse-prevention boilerplate: a session being sent control calls at an inhuman rate is itself a detection signal, which cuts directly against the reason this project exists (section 1). The exact mechanism can be worked out during implementation, but the intent should be on record now rather than left as a silent gap, the same way other open items are tracked in section 11 rather than just omitted.

Session teardown is always an explicit act — an agent calling close, a human running it from a shell, or a deliberately configured idle-timeout reaper acting only as a safety net for a harness that died ungracefully without running its own cleanup. It must never be an automatic side effect of a client merely disconnecting; a flaky network hiccup should not cost someone their running desktop. The idle-timeout reaper needs a concrete default rather than existing only as a named mechanism — a reasonable starting point is a per-scope-configurable window (defaulting to something on the order of an hour of no control calls on a session), since on the shared/central deployment specifically, idle sessions are still consuming GPU resources shared across every other caller.

**On what config-level restrictions can and can't actually guarantee, stated plainly so nobody later assumes more than is true:** a tool allowlist, a session quota, a read-only-mounted config file — none of these are a security boundary against an agent that can execute arbitrary code in the same place dAIorama runs. The compositor's virtual-input and screen-capture protocols grant capability to any client holding a socket connection; they do not check whether the request came through dAIorama's own CLI or config at all. A determined, code-executing agent doesn't need to compile its own copy of dAIorama to get around a restriction — a few lines of code talking to the same protocol directly gets the same access. A read-only-mounted config genuinely guarantees one specific thing: nothing inside the container can alter the policy dAIorama itself honors. It does not and cannot guarantee that nothing inside the container can exceed that policy some other way. These restrictions are worth having anyway, as harm reduction against bugs and as a way to give a well-behaved agent a clear, correctable error — not as a wall against something actively trying to get around them. The real security boundary is, and must remain, the container/OS isolation layer around the whole thing.

**Shell command execution is explicitly not something dAIorama should ever grow.** Launching a program on the desktop is already covered by Hyprland's own `exec` dispatch action, which is just one more entry in the control surface, not a separate feature. General-purpose shell access belongs to whatever the harness already provides for that (an existing socket-based tool, SSH, etc.) running in the same environment — dAIorama's own blast radius should stay scoped to the desktop, not grow into a second capability surface.

### 4.4 The dashboard (a "museum")

The dashboard is a deliberately separate, later-phase, fully optional component, and it should have **no special coupling to the manager at all** — it's built entirely on the same generic query API that session and control commands already need to exist (list sessions, get session detail, recent history), just potentially calling it many times over, against many managers, possibly remote ones. The manager needs zero dashboard-aware code for this to work; the dashboard is just another client.

A connection between a dashboard and a manager can be established in either direction, because each direction solves a different reachability problem: `daiorama dashboard connect <address>`, dashboard-initiated, is the simpler case and works whenever the dashboard can reach the manager directly (same LAN, same tailnet). A manager reporting to a configured dashboard URL is the one that matters when the manager is behind NAT and can dial out but can't be dialed into.

Scope, described by the person who designed it: a GUI session manager with a tab per running daiorama on the left, a center pane that nests the live VNC view when one's requested (with a button to start one on demand even for a session that wasn't created with `--view`), a history pane on the right showing session and control calls tagged by their origin, simple controls across the top (stop session, start/stop view, "take over," rename), and a home tab for the dashboard's own config and overall status. Given how much real state and logic that is — this is not a thin index page — it must be explicitly served (`daiorama dashboard serve` / `daemon start`), never something that silently springs into existence as a side effect of a session's `--view` flag or anything else. `--view` only ever starts that one session's own VNC; the dashboard is a completely separate decision. Starting a view on demand for a session that wasn't created with `--view` is the exact same child-process mechanism described in 4.1, PDEATHSIG included — it's just forked later than session creation, not a different code path.

**On the VNC connection specifically:** any session with `--view` active is independently reachable at its own address, wayvnc plus a minimal noVNC page, with no dashboard required at all — building the dashboard's own embedded viewer should still be its own genuine noVNC widget fed by websocket data, not a raw `<iframe>` pointed at that external address. That's the right place to put the abstraction boundary: today it might just open a plain direct connection, but building it this way from the start means a future relay or reverse tunnel (for cases where a session is reachable by the manager/dashboard but not directly by whoever's browsing) can be swapped in underneath later without changing how the viewer itself works. The actual networking/reachability problem for cross-network dashboards is explicitly left as the user's own problem for now — solving it properly means tunneling over a connection the session already opened outbound, which is a real, separate feature to build deliberately later, not something to bolt on speculatively now. The VNC port itself follows the exact same exposure rule as the manager's own port (section 6): loopback by default, non-loopback binding gated behind the same auth token. This wasn't stated clearly enough before — the networking section described the rule for the manager's port and `--view`'s port needs the identical treatment, not a separate, looser one by accident.

**wayvnc dying is a different failure than Hyprland dying, and shouldn't get the same response.** The desktop session and everything running on it is still alive and fine if only wayvnc crashes — only the view is gone. Marking the whole session dead over a VNC crash (section 9's policy for Hyprland) would be needlessly destructive; silently doing nothing would leave a session that looks viewable but isn't. The right policy: mark the session's view as down, leave the session itself running, and let a fresh view start the same way the on-demand case already works.

**Packaging**: the dashboard should be a genuinely separate, optionally-installed module (`dashboard install`), not a compile-time feature flag on the core binary. Since most people will be pulling a prebuilt binary from GitHub Releases rather than compiling from source, a feature flag doesn't actually shrink anyone's download unless multiple release variants are shipped — a real separate module does shrink the default download for everyone who never touches the web UI, which is the actual point.

Suggested stack if built: Dioxus in its server-rendered/fullstack mode rather than a WASM single-page app — the actual UI (a session list and a detail pane) doesn't need client-side hydration, it needs server-rendered pages plus noVNC's own existing JavaScript embedded for the viewer itself. This avoids pulling in a WASM build toolchain for something this simple. For styling, Tailwind's standalone CLI binary rather than its npm-based pipeline, which gets the same utility-class ergonomics with zero Node/npm involvement in an otherwise pure-Rust project.

### 4.5 Config

A single RON file (not JSON), edited three ways depending on the situation: `daiorama config get <dot.path>` / `config set <dot.path> <value>` for scripting and one-liners, `config edit` (just opens `$EDITOR` on the file) for anyone who'd rather edit it directly, and `config setup` as a guided interactive wizard for first-time setup. Nested keys are addressed with dot notation (`remote.default`, `session.max_sessions`), but the schema itself should be kept deliberately shallow — at most one level of nesting. This isn't just tidiness: dot-path addressing gets genuinely awkward the moment something needs to reach into a list (`foo.bar[2]`-style indexing, which is really a small query language nobody asked for), and staying shallow is what keeps `get`/`set` as simple as they look.

**This shallow rule applies to core settings — it does not and structurally cannot apply to scope definitions.** Per-scope quotas and tool manifests (4.3, 5) are inherently keyed-and-nested (one entry per scope name, each holding a quota value and a list of granted tools), which is two levels of nesting plus a list — exactly what the shallow rule exists to avoid. Rather than stretch the dot-path mechanism to cover something it was deliberately kept too simple for, scopes get their own file (or one file per scope, under a `scopes/` directory), edited directly via `config edit`-style access rather than through `get`/`set`. This is consistent with how everything else in this design gets its own natural home instead of being forced into one shape — session history already works this way. Core config stays the simple dot-path file described above; scope definitions are a deliberately different, list-tolerant mechanism, set up once per agent rather than scripted with frequent small changes. A version field on the config schema, checked at startup with a clear migration path if it's ever bumped, is worth having even though nothing forces a schema change yet.

## 5. Tool exposure model (MCP)

Two separate questions that are easy to accidentally conflate, and should stay conflated in neither the design nor the code:

1. **What can dAIorama do, internally?** This should grow to be comprehensive over time — essentially the full useful range of Hyprland's IPC surface: window management (focus, move, resize, workspace assignment), input (mouse, keyboard, clipboard), screen observation, query (list windows/workspaces), and launching programs. There is no reason to artificially cap this registry once the underlying plumbing exists, since adding one more mapped action to an existing registry is genuinely small, incremental work.

2. **What gets exposed as an MCP tool to a specific connected caller?** This must stay a separate, per-scope configurable manifest — mixed and matched by category or by individual tool, fully open to combine however a given deployment wants. A larger available tool surface measurably makes a model worse at picking the right tool; this isn't a hypothetical, it's a known problem in agent tool design. Default posture is nothing exposed until a scope's config explicitly grants categories or individual tools — deny-by-default, for the same harm-reduction reasons as everywhere else in this design.

**One deliberate exception to deny-by-default, and it needs to be stated as one, not left as an apparent contradiction.** A small, always-on session-lifecycle toolset — create, close, list, status, scoped to the caller's own sessions by the normal scope rules — sits outside the deny-by-default desktop-control manifest. Without this, an agent with nothing granted yet has no way to even create the session it would need an error to tell it to create (4.3's "an invalid ID gets a clear error telling the caller to create a session first" doesn't work if creating one isn't reachable either). Desktop control — everything that actually does something to or observes a running session — stays deny-by-default exactly as stated. Bootstrapping your own session isn't desktop control.

Keeping the internal-capability and exposed-manifest questions separate from the start is what allows dAIorama to become comprehensive in capability without ever forcing that growth onto a narrow-purpose agent's tool list. The initial, essential set to build first: window management, input, **screen capture** (an agent operating a desktop has no way to decide what to do next without some way to see it — this isn't optional alongside the others, it closes the observe-then-act loop the whole tool surface exists to support), query, and program launching — genuinely optional and less commonly needed things (decoration settings, animation curves, monitor arrangement, dynamic multi-monitor/resolution changes mid-session) can wait for a later expansion phase without blocking anything.

**Visual and audio data uses MCP's own standard content types, not a custom datatype or stream protocol.** A screenshot tool returns an `image` content block (base64 data plus a `mimeType`) directly in the tool result; a `clip_audio` tool returns an `audio` block the same way. The MCP spec defines exactly these content types for a tool result — text, image, audio, resource links, and embedded resources — and nothing else, so using them means any MCP-capable harness already knows how to receive the result with zero dAIorama-specific handling. There is no native video content type in the spec, so a `clip_video` tool should return a resource link (a URI the caller fetches separately) rather than attempting to inline video data the way image and audio can be — this is the spec's own intended shape for anything too large or unusual to carry inline, not a workaround.

**Capture is ephemeral by default; storage is a separate, explicit per-scope opt-in** — the same principle already governing history logging (4.1), applied to a heavier kind of data. A screenshot or clip exists only long enough to be served as that call's response, then it's discarded; nothing writes it to disk unless a scope's config explicitly enables audit storage (e.g. `audit.store_screenshots`, `audit.store_clips`). When enabled, it's the exact same captured artifact that was already returned, additionally persisted — not a second, separate capture. This matters more here than for the text log: meaningfully-sized, uncapped media storage is a much bigger disk and SSD-wear problem than a plaintext call log ever was, and it deserves the same explicit, scoped decision the log's own retention window already required rather than silently happening by default.

**Continuous real-time audio/video is deliberately not an MCP tool-call concern, and that's the correct seam, not a gap to patch later.** MCP tool calls are request-and-response; a persistent, continuously-updating perception stream is a fundamentally different interaction shape, and expressing it as a tool call that never returns would mean fighting the protocol rather than using it. This doesn't need a new mechanism: the VNC stream already built for `--view` (4.4) is already a standing, addressable, protocol-standard video feed, and a realtime-capable consumer connects to that exact same stream directly, the same way a dashboard or a human's browser would, just with a different kind of thing on the receiving end. dAIorama's responsibility stops at "the stream exists, at a known address, in a known protocol" — what consumes it, continuous perception steering its own tool calls included, is entirely the harness's concern, not dAIorama's.

**The actual bridge between the two worlds is one idempotent MCP tool, `get_view`: scoped to a session, starts a view if one isn't already running (the same on-demand mechanism as 4.4), and returns its address either way.** A harness asks once, discretely, over MCP; a realtime consumer then talks to that address directly for the duration of its perception loop and never touches MCP again for that purpose. This is desktop control, not bootstrapping — starting a view costs resources and opens a network-reachable port, a real action on a session rather than session self-management — so it lives in the regular, scope-configurable manifest alongside screen capture and window management, deny-by-default like everything else there, not in the small always-on session-lifecycle set from earlier in this section. The address it returns, once exposed beyond loopback, is gated by the same manager-level token as everything else (section 6), not a separate per-session credential.

Audio has no equivalent standing stream yet, which is the same audio-virtualization item already named as a deliberate v1 cut in section 10 — `get_view` only ever returns a video address until that's built. If and when it is, it should take this same shape, a standing stream a realtime consumer connects to directly, rather than a new MCP tool trying to carry continuous audio through a request/response call.

## 6. Networking and remote access

**Local:** the manager's unix socket requires no additional *transport-level* authentication, ever — nothing gates who may *open the connection* beyond filesystem permissions on the socket file, the same reasoning behind `/var/run/docker.sock` never asking for a password either. It should be reachable with zero configuration the moment it exists; that's the expected out-of-the-box behavior. **This is not the same claim as "there's no caller identity once connected."** Scope (4.3) is an application-layer field carried on every RPC call, local or remote — every request names which scope it's acting as, and the manager enforces quotas and tool manifests against that field regardless of which transport the call arrived over. "No additional authentication" describes the socket's connection-level gate specifically; it says nothing about whether a given local connection can act as a particular scope, which is a separate, always-enforced check. This distinction matters concretely the moment more than one differently-trusted process shares a machine, which section 4.3 already names as a real scenario, not a hypothetical.

**Remote:** anything reachable over the network — a session's exposed `--view` port, `daiorama serve` bound to a non-loopback address, the dashboard — is a fundamentally different trust boundary, and securing it is explicitly the user's own responsibility, not something dAIorama implements on their behalf. Concretely:
- Binding to any non-loopback address requires an auth token to already be configured. One is generated automatically on first use if none is set. The manager refuses to start bound non-locally without a token configured — a loud failure at startup, never a silently open port. **This same rule applies identically to a session's `--view` port**, not just the manager's own RPC port — loopback by default, the same token gate the moment it's bound further than that. One consistent exposure rule, not two by accident.
- The token's own handling needs to be concrete, not just "a token exists": it's stored in its own file with restrictive permissions, separate from the general config file (not something that ends up casually edited or committed alongside ordinary settings). A remote client supplies it via an environment variable alongside `--remote` (`DAIORAMA_TOKEN` or similar) rather than as a CLI argument, so it never lands in shell history or a process listing. It's scoped per-manager — one shared secret gating whether a caller may talk to a given instance over the network at all — not per-scope; scope identity (above) is a separate, finer-grained concept that applies after this coarser network gate, not instead of it. Rotating it is just regenerating the file and restarting the manager; there's no running-state to migrate since nothing caches it beyond the current connection.
- dAIorama does not implement TLS or any of its own certificate handling. This is deliberate, not an oversight: getting this right is genuinely hard, and getting it subtly wrong (a forgotten flag, a skipped verification step) has a well-documented history of turning into real, serious exposure — Docker's own remote API had years of exactly this problem. The documented, recommended pattern instead is to run remote access over an overlay network that already provides real encryption and identity (a WireGuard-based network like Tailscale), and/or to put a mature, purpose-built reverse proxy in front for TLS termination if broader exposure is genuinely needed. Reuse tools that have already been through real adversarial use instead of building novel cryptography for this.

**The `--remote` flag:** every command that talks to a manager (`new`, `close`, `list`, `control`, `config get`/`set`, etc.) carries an optional `--remote=<address>` flag meaning "which manager instance is this command talking to." There is exactly one meaning for this flag across the whole CLI — it does not need a separate concept per component, since `--view` is a property of a session that already lives on whichever manager is being targeted (it doesn't have its own remote target), and the dashboard already has its own separate connection mechanism (`dashboard connect`). A persistent default lives in config (`remote.default`, set with the ordinary `config set` command — no separate wrapper command needed for this), and the flag on any individual invocation overrides that default for just that one call. Standard hostname resolution — DNS, `/etc/hosts`, container-network names, Tailscale MagicDNS names — all work automatically, since this is just an ordinary client connecting to whatever address it's given; dAIorama does not need any resolution logic of its own.

`--remote` should accept either a `host:port` address or a literal unix socket path. This isn't two features — it's one flag learning to accept two shapes of address, and it's what makes the runtime-directory interop case described below fall out for free instead of needing its own code (see 7.2).

## 7. Runtime directory and socket handling

### 7.1 The problem, and the default fix

`$XDG_RUNTIME_DIR` is the correct location for exactly this kind of thing — transient runtime sockets, not persistent config or data — and it needs no root at all; it's normally `/run/user/$UID`, tmpfs-backed, cleared on logout. It's also literally where Hyprland already puts its own per-instance sockets, so dAIorama's manager socket lives right next to it for a natural, useful consistency.

On a real login, this is already set up automatically by systemd or elogind. **Inside a container, nothing does this automatically** — there's no login session to set it up — so this can't be assumed to exist. The fix belongs in dAIorama's own startup code, in one place: check whether `$XDG_RUNTIME_DIR` is already set and usable, and if not, create an equivalent fallback directory itself (same permission model, container-local) before doing anything else. Because dAIorama is the parent process that forks Hyprland, whatever it sets in its own environment before that fork is what Hyprland inherits automatically — there is no need for Hyprland to have any separate detection logic of its own. One check, one place, covers both bare-metal and containerized deployment.

The shipped container image's own entrypoint can additionally pre-create this directory and export the variable ahead of time as a belt-and-suspenders default for the common OOTB case, but that's a convenience, not the load-bearing fix — the real fix living in dAIorama's own startup code is what makes this correct everywhere, including for anyone who installs dAIorama bare and runs it in a context this document didn't anticipate.

### 7.2 The interop side effect (not a default, not something to build specially)

Because the manager's startup logic already has to check "is a socket already here before I create a new one" (this is also what makes lazy manager discovery work at all), that same check produces an interesting, entirely optional side effect for free: if someone bind-mounts a *real host directory* into the container at that same runtime-socket path, instead of letting dAIorama create a fresh container-local one, whatever's already there — Hyprland's socket, dAIorama's own socket, or both — gets found and used exactly as if it had been created locally. No new code is needed for this to work; it's the same discovery check finding a different thing depending entirely on how the compose file was written. This means a host's own real Hyprland session and a container's dAIorama instance can end up directly interoperating, purely as an emergent property of a simple, honest mechanism — not something specially built.

**This is explicitly not the default, and must never be how the shipped OOTB container behaves.** If built, document it as a deliberate, opt-in pattern using a narrow, dedicated bind-mount path — never the entire `$XDG_RUNTIME_DIR`, which also carries a real host's D-Bus session bus, keyring/secret-service socket, and other genuinely sensitive session state alongside whatever compositor sockets live there. Exposing all of that to a container to get this one interop trick would be a real, unnecessary widening of the isolation boundary this whole project is built around.

## 8. Distribution and packaging

**dAIorama's own binary:**
- Primary channel: a static Rust binary attached to GitHub Releases, installed via a plain install script. No reason a Wayland-protocol-speaking Rust binary can't be fully static and dependency-light.
- Secondary: a Homebrew tap (not aiming for `homebrew-core`), matching existing tooling conventions already in use elsewhere.
- Tertiary, essentially free once building in Rust anyway: published to crates.io, without ever expecting an end user to have `cargo` installed — this is for Rust-literate users specifically, not the primary path.
- Deliberately not chasing broader package manager coverage (nixpkgs, AUR, system `apt`/`dnf` repos) at this stage. That can happen organically later through community packaging if it happens at all.
- None of this applies to the container image path — the image just builds the binary directly, no external channel involved at all.

**Missing Hyprland/wayvnc on the bare-host install path:** these are real system compositor/display packages with real system-level dependencies (Mesa, libinput, systemd, wayland-protocols) — not something practical to vendor as a self-contained static build the way a small CLI tool can be, and not something dAIorama should try to auto-install with `sudo` on the user's behalf either. If either is missing, detect it and print the exact install command for the detected system package manager (`apt`/`dnf`/`pacman`/`brew`), and point at the container image as the alternative for anyone who'd rather not install a compositor system-wide. In practice, the bare-host install path only really makes sense for someone who already runs Hyprland day-to-day — if it's missing, that's a fairly strong signal they'd be better served by the image anyway.

**Even when Hyprland is present, its version isn't guaranteed to match what dAIorama expects.** Section 3.1 already notes Hyprland has had at least one disruptive config-format break. A bare-host install pairs dAIorama against whatever system Hyprland happens to be installed, which could have an IPC surface that's drifted from what dAIorama was built against. A startup-time version check against a known-compatible range, failing with a clear, specific error naming the mismatch, turns a confusing downstream IPC failure into an immediate, legible one — consistent with the fail-loudly principle in section 2.

**No distro-portability effort beyond this.** The container handles that concern entirely for anyone using it; the bare-host install script doesn't need to solve for every possible Linux distribution, just detect and guide clearly.

## 9. The container image

**No default `CMD`.** There are too many legitimate top-level invocations for a single default to be the right guess most of the time: a bare MCP bridge pointed at a remote manager, the full local stack for a self-contained agent desktop, just the manager exposing itself for a thin remote MCP running elsewhere, or a harness installed directly into the same image so the agent and its desktop share one container. Leaving `CMD` unset is the honest reflection of that. What must ship alongside it, so this isn't just a confusing blank page, is a small set of explicit, ready-to-copy compose snippets, one per legitimate shape, documented clearly.

**The common-case compose file** should be genuinely simple: one line for the GPU device mount, an MCP port, a VNC port, and an optional volume if persistence is wanted.

**Persistence should be scoped narrowly.** A session's own state is disposable by design — it rebuilds cleanly every time Hyprland starts, the same as any fresh desktop session would. What actually deserves to survive a container restart is specific things like a browser's profile, cookies, and logins. Mount those specifically; don't treat "the whole session" as something that needs a volume.

**Crash handling:** if Hyprland dies mid-session, the manager should not attempt to automatically restart it. An automatic restart risks quietly masking a real underlying problem behind a crash loop. Mark the session dead instead, and let a fresh, explicit `new` call create a clean one. (wayvnc dying is a separate, lighter-weight failure with its own distinct policy — see 4.4, don't apply this same "mark it dead" treatment to a VNC crash.)

**Per-session resource limits, via cgroups v2, which rootless Podman already supports delegating.** A single runaway browser tab can consume all available memory and trigger the host's OOM killer, which, without isolation, takes down the manager and every other session sharing the host, not just the offending one. Apply memory and CPU limits per session through cgroups v2 so that if a session exceeds its limit, the kernel kills only that session's own processes, leaving the manager and every other session intact. This is the better fix for transient failures like a single tab OOMing — it contains the failure instead of needing a retry/restart policy layered around the crash-handling rule above, which would risk exactly the crash-loop-masking problem that rule exists to avoid.

**The MCP bridge's network binding must support two shapes equally, not just the obvious one.** It needs to work as a published container port reached by a separate container over the network — the default, flagship shape, an agent's own container reaching dAIorama's container — and as localhost or a mounted unix socket reached by a harness installed directly inside the same image, so an agent and the desktop it controls can share one container when that's what's wanted. Don't hardcode a binding assumption that only serves one of these.

**The homelab/shared-instance shape is a first-class deployment, not an edge case.** A single "central" dAIorama instance that several separate agent containers all point at via `--remote`, rather than requiring a full dAIorama embedded in every single agent's own container, should work with zero special handling — it's the same manager, the same session registry, just serving more than one caller. The dashboard's cross-manager aggregation exists specifically to make monitoring this shape practical: one URL to check instead of one per agent container.

## 10. Explicitly out of scope

Stated plainly so these don't get accidentally built in later out of a sense that "more coverage is better":

- **General shell/command execution.** Program launching on the desktop is covered by Hyprland's own `exec` dispatch action, already part of the control surface. Anything beyond that — arbitrary shell access — belongs to whatever the harness already provides in the same environment.
- **TLS, certificate management, or any of dAIorama's own cryptography.** Deliberately delegated to overlay networks and reverse proxies that already do this well. See section 6.
- **Broad package manager coverage** beyond GitHub Releases, a Homebrew tap, and crates.io, at least for now.
- **A full, un-curated exposure of every Hyprland IPC action at launch.** The internal registry can and should grow toward comprehensive over time (section 5), but what ships and is exposed by default at first is the essential set: window management, input, query, program launch. Decorations, animations, monitor arrangement, and similar can come later without blocking anything.
- **Relay/tunneling for the dashboard's remote VNC connections**, beyond the architectural provision to add it later (section 4.4). Building this properly means a real reverse tunnel over an already-open connection, which is a deliberate, separate feature, not something to improvise as a side effect of the dashboard viewer.
- **File transfer in and out of a session.** Section 9 covers persisting a browser's profile, cookies, and logins across restarts — that's a *persistence* problem, and it's deliberately scoped narrowly. Getting a file an agent downloaded inside a session (a PDF, an export) out to wherever the harness runs, or pushing a local file in for an upload flow, is a different problem, *transfer*, and it's real and will come up in ordinary browser-automation work. Named here as a deliberate deferral rather than left unmentioned, not solved now.
- **Audio device presence, and dynamic mid-session display changes.** A real machine almost always has an audio device; a headless session with none present is itself a minor fingerprint, the same category of signal as the renderer string in 3.4, though with less immediate payoff. Full audio virtualization (capture, injection, PipeWire integration) and dynamically adding/removing virtual outputs or changing resolution after a session has already started (as opposed to setting it once at creation, which is in scope, see 3.3) are both reasonable future directions, deliberately cut for v1 rather than silently absent. If audio virtualization is built later, it should follow the same standing-stream shape the VNC feed already uses for video (section 5) — a realtime consumer connects directly, it doesn't go through an MCP tool call.
- **Live, zero-downtime upgrades of a running manager.** On the shared/central deployment shape, upgrading the manager binary necessarily means briefly dropping its active sessions — there's no re-attachment or handoff mechanism that lets a new manager process adopt another process's already-running, PDEATHSIG-linked children without dropping and re-establishing that linkage, which is real complexity in service of a benefit this project's actual scale doesn't need. Document the tradeoff plainly (updating a shared instance drops what's running on it; avoid doing it while agents are actively using it) rather than building hot-swap infrastructure sized for a multi-tenant platform this isn't.

## 11. Unknowns and things to verify during development

These are things that genuinely need resolving during implementation, not decisions this document is dodging — each one got real research during design, but the honest answer in each case is "this needs to be confirmed against the real environment," not a settled fact to build on top of blindly.

**The first item below is the load-bearing one and should be treated as a P0 spike, done before investing further implementation effort anywhere else — not one item in a list to get to eventually.** Everything else in this document, the manager, the bridge, the dashboard, the whole MCP surface, assumes headless Hyprland with rootless GPU access actually works. Prove the full chain end to end — rootless Podman, render-node access, Hyprland headless, virtual pointer and keyboard, screen capture, wayvnc, noVNC, and a real (non-`llvmpipe`) WebGL renderer string in an actual browser — before building much on top of the assumption that it does. If that chain doesn't hold together, the fallback path (niri, or a nested-compositor workaround) needs to be real and tested, not aspirational.

- **GPU device passthrough for AMD/Intel in a container, and headless Hyprland itself** (see 3.3, 3.4). Current documentation still points at `--device /dev/dri/renderD128` plus `--group-add keep-groups` plus an SELinux boolean on Fedora-family hosts, but there are real, currently-active Podman issues around group mapping in this exact area, and genuine disagreement between the upstream default device permission mode and what's actually observed on real machines. Don't build a hardcoded recipe against this — check the actual permissions and group requirements on the real target machine (starting with `ls -l /dev/dri/renderD128`) and treat whatever's found there as the source of truth over anything written here. Separately, whether Hyprland's dedicated headless-output feature is stable enough to use directly, or whether the render-only DRM/TTY path needs to be the real default under the hood, is part of the same spike. However this resolves, it needs a repeatable way to verify going forward, not just a one-time check — plan for protocol-level tests against the `headless` backend under software rendering as a correctness check that can run in CI, distinct from whatever necessarily needs real GPU hardware in the loop and can only be verified manually or on real target machines.
- Whether wayvnc's own websocket support serves noVNC's actual HTML/JS page, or only the raw RFB-over-websocket data channel with the static page needing to come from somewhere else. Confirmed during design that it's likely just the data channel — plan for a small companion static file server either way, and don't assume it's free.
- Exact command names, internal struct names, file paths, and similar naming details are intentionally left open here. The plan is to work through those against a concrete first draft rather than deciding them in the abstract — they should be settled as a pass over the actual implementation, not re-derived from this document from scratch.
